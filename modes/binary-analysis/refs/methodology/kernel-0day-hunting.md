# 内核 0day 挖掘方法论（NDIS/KLoader 范本）

> 范本：CVE-2026-62737（Windows 11 25H2 最新版仍可用的内核提权 0day，原创挖掘全过程见
> xz.aliyun.com/news/92658）。本文件提炼**可复用的找洞流程**，供"主动挖内核洞"任务对照；
> 样本分析/逆向还原视角见本目录其他文件。

## 1. 目标选择：代理层 = 系统性错误富矿

- 选**承上启下的枢纽组件**（范本选 NDIS：Miniport/协议驱动/Filter/NetAdapterCx 大量模块注册其中）；
- 核心判断：**"一个组件替另一个组件接待调用方"的架构，访问控制最易出系统性错误**——ACL 往往只绑
  最终对象，代理层经常忘记重新做授权判断；
- 推论（审计提问）：目标系统里还有哪些"转发/代理/总线"型设备？（对象管理器目录里的中间层设备、
  按名转发 IOCTL 的 multiplexer 都算。）

## 2. 代理路径发现与"ACL ≠ 不可达"

- 在枢纽驱动里找**路径语法型入口**（范本：`\\.\kloader\{GUID}` 按模块 GUID 转发 create/IOCTL）；
- 关键判定：**设备有 ACL 不等于不可达——ACL 只保护直接打开那一条路**；被代理注册的模块等于
  从背后重新暴露给低权限用户；
- 注册表坐实：父键限制枚举 ≠ 限制直接路径查询（范本：枚举报无权限，完整路径直查子键可读）；
  GUID → 目标驱动的映射从注册表拿。

## 3. IOCTL 面枚举优先级

WDF 驱动从 `EvtIoDeviceControl` 入手逐个列 IOCTL，**按风险排序细读**：

1. 接收用户输入并**创建/注册内核对象**的 IOCTL（最前）；
2. 携带**回调/函数指针**字段的注册类；
3. 纯配置读写 knob 类（最后）。

## 4. 数据流定性：范围检查不是信任证明

- 范本形态：用户缓冲区两个 QWORD **原样写入**池对象 → 消费端执行前唯一校验
  `Callback >= MmSystemRangeStart`；
- 定性原则：**数值范围检查只回答"地址落在哪段地址空间"，回答不了"这个地址是谁注册的、调用方
  有没有权让内核执行它"**——范围检查=分类，不是信任证明；
- 消费端必追：写入本身不定性，**看谁解释它**（系统线程循环取任务直接 `Callback(Argument)`）。

## 5. 同类错误枚举（一个洞后的第一动作）

找到主路径后**把同驱动里所有"用户输入 → 回调指针"路径过一遍**——范本同驱动三处同类
（QueueTask / EnterKernel / SetKmNotifications）。判定根因级别：**"用户协议允许携带原始内核
函数指针"这个设计本身是病根**——出现在哪个函数，哪个函数就出问题。

## 6. PoC 闭环：唤醒坎与双标记证据

- 静态证据链完整 ≠ 可达——范本的坎是**内核线程不消费队列**：Initialize 有严格前置校验
  （用户指针/线程句柄/事件句柄都要真），任务入队后需要事件唤醒（解法：注册用户线程退出回调，
  短命线程退出触发清理路径置位事件）；
- PoC 标记设计：Callback=可辨认值（0x...41414141）、Argument=0x1122334455667788——
  **崩溃栈里 RIP/RCX 双命中预设标记 = 低权限输入真实抵达的闭环证据**；
- 利用条件如实评估：范本单漏洞受 KASLR 约束（新版本 NtQuerySystemInformation 已不可本地泄基址），
  需搭配基址泄露漏洞——**提权链完整性单独评估，不夸大单洞**。
