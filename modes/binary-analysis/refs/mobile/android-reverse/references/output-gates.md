# 回复与完成门禁

本文件只约束用户可见主张的精度。正常进度回复、工具说明和阻塞说明可以直接输出；只有“已完成、已成功、已交付、已验证”等结论必须通过完成门禁。

## 进度回复

进度回复应简短包含：当前证据、它如何改变路线、下一可执行动作。不要为了满足模板重复工具清单、已读文档列表或尚未发生的完成检查。

以下情况应主动回复，而不是继续静默执行：

- 需要用户登录、触发页面、提供样本或恢复设备
- 操作可能清数据、覆盖安装、触发真实短信/支付/生产流量
- 用户指定且无等效替代的工具不可用
- 止损条件触发，需要说明失败证据和 pivot
- 获得足以改变路线的关键证据

遇到有等效替代的普通工具错误，可以记录后切换，不必停下请求许可。

## 证据落盘

会被用于根因、patch 或完成判断的主张，先写入 `run/fixtures.json` 或对应日志，再通过 `task-record-attempt` 更新 `state/route-state.json`。`state/clues.md`、`state/route-plan.md`、`state/progress.md` 是生成视图，不要手工双写。

下列发现应在下一轮推理依赖它之前落盘：

- 已验证的算法、密钥材料或协议结构
- 已识别的壳、混淆或检测机制
- 已闭合的 Java↔JNI↔Native 调用链
- patch 根因和回滚依据

正文可用 `[突破落盘] CLUE-N | 摘要` 告知用户，但标注不是完成证据。

## 搜索判断

遇到未知商业壳、未知 SDK、无法识别的算法族或连续两次同类观察没有新信息时，查阅当前资料并记录来源。搜索是解决具体未知量的手段，不是每次回复前的仪式；状态更新或安全阻塞说明不应因尚未搜索而被禁止。

## 完成声明

准备声明某个 deliverable 完成时依次执行：

1. 读取 `task.json`，确认 `objective`、该 deliverable 的 `tier`、`criteriaIds`、否决路线和运行时依赖限制。
2. 逐条确认相关 `completionCriteria[].status` 精确为 `met`，且 `evidenceRefs` 可读取。
3. T5/本地复现任务运行 `task-verify`，确认结果与当前 spec 和入口文件哈希一致；T3 确认 no-op 重签基线和任务特定回归矩阵。
4. 只有最终用户/设备边界尚未验证时，将状态写为 `acceptance-ready`，不要写 `delivered`。
5. 所有必需 deliverable 都是 `delivered` 后运行 `task-close`。`task-close` 会对最终落盘状态再次验证。

完整检查项见 `references/completion-gate-checklist.md`。

## 主张精度

- `provisional`：静态推断或单次观察
- `route-ready`：证据足以选择下一路线
- `acceptance-ready`：agent 侧验证完成，仍缺用户或真实设备边界验收
- `delivered`：契约中的全部必需验证已通过

禁止把“找到函数”“脚本退出码为 0”“打印了预期字符串”“用户尚未执行的步骤”写成已交付。没有对话证据时，不得写“用户已确认”。
