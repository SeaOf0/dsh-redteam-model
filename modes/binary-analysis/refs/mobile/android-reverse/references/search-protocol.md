# 搜索协议

本文档包含搜索相关的完整操作规范。SKILL.md 中保留了触发条件骨架，本文件提供详细格式和执行规则。

## 一、搜索门禁（回复前硬检查）

准备输出任何用户可见回复前（包括阶段性回复、完成声明、失败报告），必须先通过以下搜索相关检查项。任一条件命中即**禁止回复**，必须先执行搜索后再继续：

1. **保护信号未搜索**：`route-state.json` 的 `search.searchRounds` 为 0 且累计执行 >= 3 轮，且存在壳/加固/商业保护/商业 SDK 信号（如识别到加固厂商名、壳特征、商业反调试 SDK）→ 立即通过 `WebSearch` 搜索：从当前任务的壳名/包名/SO名/特征字符串中提取 2~3 个关键词作为 `query`
2. **高对抗未搜索**：防护等级 A4+ 且 `search.searchRounds` 为 0 且累计执行 >= 3 轮 → 立即通过 `WebSearch` 搜索：`query` 为包名 + 加固/壳 + 关键症状词
3. **纠偏未搜索**：连续 2 轮无任何阶段进展，且 `search.searchRounds` 为 0 → 立即通过 `WebSearch` 搜索：`query` 为包名 + 当前分析的核心函数名或特征

## 二、搜索后落盘序列

每次 `WebSearch` 调用后，必须立即（中间不得插入任何非 Read 类工具调用）执行以下 3 步：

### 步骤 1：追加搜索结果

`Edit` 追加搜索结果到 `artifacts/tasks/<task-id>/state/external-research.md`（若文件不存在则先用 `Write` 创建，此后只能 `Edit` 追加，禁止覆盖已有段落）。每次搜索产生独立的 `## Round N` 段落，必须包含：

- `query:` 实际搜索 query（原文）
- `sources:` 至少 1 条来源 URL
- `findings:` 至少 1 条具体发现（>=20 字符，禁止含"相关/一些/有效/无结果"等模糊词）
- `usedFor:` 本次发现如何影响下一步操作

### 步骤 2：更新路由状态

`Edit` 更新 `route-state.json` 的 `search.searchRounds`（值必须等于已执行的 WebSearch 调用总次数） / `search.lastSearchRound`（当前轮次） / `search.searchDecision`（搜索结论，>=20 字符）

### 步骤 3：正文输出

正文输出 `[搜索落盘] query: X, 结论: Y, searchRounds: N`

**以上 3 步未全部完成前，禁止继续任何分析操作或输出搜索结论给用户。**

**落盘预任务间隙**：若 `route-state.json` 尚未创建，按通用落盘前置规则创建。

## 三、执行内搜索检查

**在每轮分析操作结束后、下一轮操作或新切入点开启前**强制执行，不等到回复门禁。以下任一条件命中即**立即通过 `WebSearch` 执行搜索**，不得继续深挖局部模式，不得新开切入点，不得进入下一轮分析：

| 触发条件 | query 参数 | context |
|---|---|---|
| 商业加固/壳/保护方案无法快速识别 | 壳名 / 保护 SDK 名 / 特征字符串 | "保护识别" |
| Native SO 中的加密算法族无法快速识别 | 符号名 / 常量特征 / 函数名 | "算法族识别" |
| 出现未知的商业 SDK / 第三方库 | SDK 名 / 包名 / 特征类名 | "SDK识别" |
| 遇到未知防护手段 | 检测函数名 / 特征字符串 | "防护识别" |
| 连续两轮未逼近验收 | 包名 + 关键函数名 | "纠偏搜索" |
| 命中商业壳/加固/保护方案的高信号 | 壳名 / 加固厂商名 | "保护识别" |
| 用户明确要求查资料 | 用户给出的关键词 | "用户请求" |
| 不确定是否命中以上条件，但缺少外部信息 | 包名 + 关键症状词 | "方向确认" |

**调用方式**：直接调用 `WebSearch` 工具，参数只有一个 `query`。如果需要限定搜索范围，可以在 query 中追加 `site:github.com` 或 `site:52pojie.cn` 等限定词，但不使用 `allowed_domains` 参数。

搜索关键词直接用已观察到的具体值（壳名、符号名、包名、特征字符串），不知道确切名称就用 APK 包名或 SO 文件名。搜索结果需深入阅读时通过 `mcp__web_reader__webReader(url="...")` 获取全文。

搜索完成后：执行与本文件"二、搜索后落盘序列"相同的 3 步落盘序列。搜索用于加速识别保护方案/算法族/SDK/公开协议，不能代替 Frida 动态取证、smali 分析与最终验证。

## 四、搜索 query 参数填充优先级

当触发搜索但缺少具体标识时，按以下顺序填充，禁止传空 query：

1. 有具体壳名 / SDK名 / 函数名 / 符号名 → 直接使用
2. 无具体名但有 APK 包名 → 使用包名 + "逆向" / "加固" / "签名" 等限定词
3. 无包名但有 SO 文件名 → 使用 SO 名 + 关键症状词
4. 以上全无 → 使用用户原始描述的前 5 个关键词

## 五、搜索轮次上限

**同一卡点最多搜索 2 轮**。超过 2 轮仍未解决当前问题时，禁止继续搜索，必须切换到其他分析方法。

**定义**：
- **一轮搜索** = 一个 turn 内对同一卡点的所有搜索调用。每个 turn 对同一卡点最多发起 1 次 `WebSearch` 调用——等结果返回、完成落盘后，才允许发起下一轮搜索。禁止在同一 turn 内并行发起多次搜索
- **同一卡点** = 针对同一个未解决的具体问题（如"mtgsig 算法还原"、"libmtguard SO 混淆分析"、"某某壳脱壳"）。卡点以**目标对象**（SO名/函数名/壳名/SDK名）为粒度划分，不以搜索关键词不同来区分。同一目标对象上的不同搜索关键词视为同一卡点

**计数与触发**：
- 每次搜索后落盘时，在 `route-state.json` 的 `search` 对象中维护 `searchByStuckPoint`：`{ "<stuckPointDesc>": { "rounds": N, "resolved": false } }`
- 当 `rounds` 达到 2 且 `resolved` 仍为 `false` 时，禁止对该卡点继续搜索
- 若搜索直接解决了问题（如找到了公开算法实现、找到了脱壳工具），设 `resolved: true`，不计入上限

**超过上限后的强制路径**：
1. **有对应 playbook**（如 OLLVM → `deobfuscation-playbook.md`，VMP → `vmp-analysis-playbook.md`）：必须 `Read` 对应 playbook 并按其工作流执行
2. **无对应 playbook**：pivot 到其他分析方法（IDA 深度分析、Frida 动态取证、smali patch 等），不得在搜索上继续停留
3. 正文必须输出 `[搜索上限] 卡点: X, 已搜索 2 轮未解决, 切换到: Y`

**例外**：用户明确要求继续搜索时（"再搜一下 X"），重置该卡点的计数器。但模型不得主动暗示用户这样做。
