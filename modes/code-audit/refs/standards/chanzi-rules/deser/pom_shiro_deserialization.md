## Java Shiro反序列化漏洞
Apache Shiro是Java领域广泛使用的安全框架，提供身份认证、授权、会话管理、加密等核心功能，其反序列化漏洞是影响范围极广的高危安全问题，核心根源在于对序列化数据的不安全处理，攻击者可通过构造恶意序列化payload实现远程代码执行（RCE）等严重危害。以下从漏洞根源、触发条件、不同版本/场景的漏洞变体、攻击链路、影响范围等维度完整描述。

## 一、漏洞核心根源
Shiro的反序列化漏洞本质是**对可控的序列化数据未做安全校验直接反序列化**，核心涉及两个关键组件：
1. **CookieRememberMeManager**：Shiro的“记住我（RememberMe）”功能默认实现类，负责将用户身份信息序列化后加密存储在Cookie中，请求时解密并反序列化数据；
2. **默认加密密钥硬编码**：早期Shiro版本（≤1.2.4）内置硬编码的AES加密密钥（`kPH+bIxk5D2deZiIxcaaaA==`），攻击者可通过该密钥解密Cookie中的序列化数据，或构造恶意序列化数据加密后注入Cookie，触发反序列化执行恶意代码；
3. **反序列化未做白名单校验**：即使部分版本修复了硬编码密钥，若未对反序列化的类做严格白名单限制，攻击者仍可通过自定义密钥（若密钥泄露/可猜测）构造payload触发漏洞。

## 二、漏洞触发的基础条件
要触发Shiro反序列化漏洞，需满足以下核心条件（不同变体略有差异）：
1. 应用启用了Shiro的“RememberMe”功能（默认开启，可通过配置关闭）；
2. 存在可控的、经过Shiro加密/解密的序列化数据输入点（最常见为`rememberMe` Cookie，部分场景为请求参数、会话存储等）；
3. 攻击者可获取/猜测到Shiro用于加密RememberMe数据的AES密钥（硬编码/配置泄露/密钥强度低）；
4. 应用依赖的Java环境/第三方库包含可被反序列化利用的“Gadget（利用链）”（如Commons Collections、Commons Beanutils、Jackson、Fastjson等）；
5. Shiro未对反序列化过程做严格的类过滤/白名单限制。

## 三、不同版本/场景的漏洞变体
### 1. 经典版本漏洞（Shiro ≤ 1.2.4）：硬编码密钥导致的反序列化RCE
#### 核心特征
- 该版本是漏洞最原始、影响最广的变体，根源是`CookieRememberMeManager`中硬编码了AES加密密钥（Base64编码为`kPH+bIxk5D2deZiIxcaaaA==`，对应原始密钥为16字节的`\x31\x32\x33\x34\x35\x36\x37\x38\x39\x30\x31\x32\x33\x34\x35\x36`）；
- RememberMe Cookie的处理流程：
  ```
  用户登录勾选“记住我” → Shiro将用户信息序列化 → AES加密 → Base64编码 → 写入rememberMe Cookie
  下次请求 → 读取rememberMe Cookie → Base64解码 → AES解密 → 反序列化 → 恢复用户信息
  ```
- 攻击者可反向操作：构造恶意序列化payload（如包含Commons Collections利用链的字节流）→ AES加密（使用硬编码密钥）→ Base64编码 → 注入rememberMe Cookie → 服务端解密后反序列化 → 执行恶意代码。

#### 触发场景
只要应用使用Shiro ≤1.2.4且开启RememberMe功能，无需额外配置，攻击者即可利用硬编码密钥构造payload触发RCE。

### 2. Shiro 1.2.5~1.4.1：密钥硬编码修复但反序列化校验缺失
#### 核心特征
- Apache官方在1.2.5版本修复了硬编码密钥问题，默认不再使用固定密钥，而是通过`SecurityManager`的配置生成随机密钥；
- 但该版本及后续1.4.1之前的版本，**未对反序列化的类做白名单限制**：
  - 若开发者手动配置了弱密钥（如固定字符串、可猜测的密钥）；
  - 或密钥通过代码泄露（如硬编码在配置文件、代码中）；
  - 攻击者可通过爆破/猜测密钥，构造恶意序列化payload触发RCE。

#### 关键差异
与1.2.4的核心区别是“无默认硬编码密钥”，但反序列化逻辑仍不安全，属于“密钥可控下的反序列化漏洞”。

### 3. Shiro 1.4.2~1.7.0：部分修复但存在绕过/场景漏洞
#### 核心修复
1.4.2版本开始，Shiro引入了`Serializer`接口的白名单机制（默认仅允许`SimplePrincipalCollection`等核心类反序列化），但仍存在以下问题：
- **白名单绕过**：若应用自定义了`Serializer`实现，或扩展了Shiro的序列化逻辑，可能绕过默认白名单限制；
- **非RememberMe场景的反序列化**：
  - 会话存储场景：若Shiro使用`Serializable`存储会话数据（如Redis、Memcached存储会话时序列化），且会话数据可控，可触发反序列化；
  - 请求参数/表单数据：部分应用将用户输入直接序列化后存储/传输，若使用Shiro的序列化工具类，可触发漏洞；
- **第三方依赖Gadget兼容**：若应用依赖的第三方库（如Jackson 2.x、Fastjson 1.2.x）存在新的反序列化利用链，可绕过Shiro的白名单。

#### 典型场景
例如，某应用使用Shiro 1.6.0，且自定义了`CookieRememberMeManager`的`Serializer`为`DefaultSerializer`（未做额外过滤），同时密钥配置为`1234567890123456`（弱密钥），攻击者可猜测密钥后构造payload触发RCE。

### 4. Shiro 1.7.1+：修复核心漏洞但边缘场景仍有风险
#### 核心修复
1.7.1版本（含）之后，Shiro：
- 强化了序列化白名单，默认仅允许核心安全类；
- 禁用了`DefaultSerializer`的通用反序列化；
- 推荐使用`JsonSerializer`（JSON序列化，非Java原生序列化）替代默认的Java序列化；
- 对AES密钥的生成做了强制强度校验（要求16/24/32字节的强密钥）。

#### 剩余风险场景
- **自定义序列化逻辑**：若开发者自行实现序列化/反序列化逻辑，未做安全校验，仍可能引入反序列化漏洞；
- **边缘功能**：如Shiro的“密码重置”“验证码存储”等功能，若将用户输入序列化存储，且未过滤，可触发漏洞；
- **集成第三方组件**：Shiro与Spring、MyBatis等集成时，若第三方组件的序列化数据可控，且通过Shiro处理，可能间接触发漏洞。

## 四、非Cookie场景的反序列化漏洞
除了经典的`rememberMe` Cookie，Shiro反序列化漏洞还可能出现在以下场景：
### 1. 会话管理场景
- Shiro默认使用`DefaultSessionManager`管理会话，若会话存储在外部介质（如Redis、MySQL、Memcached），会话数据以序列化字节流形式存储；
- 若攻击者可篡改会话数据（如Redis未授权访问、数据库注入修改会话字段），构造恶意序列化字节流，当Shiro读取会话数据反序列化时触发RCE。

### 2. 分布式会话场景
- 分布式部署下，Shiro常使用`RedisSessionDAO`/`MemcachedSessionDAO`存储会话，序列化后的会话数据在分布式节点间传输；
- 若传输过程中数据被劫持/篡改（如未加密传输），或存储介质权限不足，攻击者可注入恶意序列化数据。

### 3. 自定义RememberMe实现
- 部分开发者自定义`RememberMeManager`实现，未复用Shiro的安全序列化逻辑，直接使用`ObjectInputStream`反序列化用户可控数据，导致漏洞。

### 4. Shiro工具类滥用
- Shiro提供`SerializationUtils`等序列化工具类，若应用开发中使用该工具类反序列化用户输入的字节流（如接口接收序列化字节数组参数），可直接触发反序列化漏洞。

## 五、漏洞利用的关键链路
无论哪种变体，核心利用链路均为：
1. **信息收集**：确定应用使用的Shiro版本、是否开启RememberMe、密钥相关线索（配置文件、代码、响应头）、依赖的第三方库（Gadget）；
2. **密钥获取/猜测**：
   - 硬编码密钥（≤1.2.4）直接使用默认密钥；
   - 弱密钥爆破（常见16/24/32字节密钥，如`1234567890123456`、应用名+数字等）；
   - 配置文件泄露（如`shiro.ini`中配置的`rememberMeManager.key`）；
3. **构造恶意payload**：
   - 根据Java版本、第三方库版本选择合适的反序列化利用链（如Commons Collections 3.2.1、Commons Beanutils 1.9.2、JRMP等）；
   - 将利用链序列化为字节流；
4. **加密/编码**：使用获取到的AES密钥对payload字节流加密，再Base64编码（适配Shiro的Cookie格式）；
5. **注入触发**：将构造后的内容注入`rememberMe` Cookie（或其他可控输入点），发送请求至目标应用；
6. **执行恶意代码**：服务端Shiro解密后反序列化payload，触发利用链执行，实现RCE（如执行命令、写入木马、控制服务器）。

## 六、漏洞影响范围与典型特征
### 1. 影响范围
- 语言：仅Java应用（Shiro为Java专属框架）；
- 部署方式：所有使用Shiro的Java Web应用（Spring MVC、Struts2、JSP/Servlet等）；
- 行业：互联网、金融、政务、企业内部系统等广泛使用Shiro的场景。

### 2. 典型特征（可用于漏洞探测）
- 响应头包含`Set-Cookie: rememberMe=deleteMe;`（开启RememberMe但未勾选时的默认响应）；
- 存在`/shiro`相关路径，或配置文件包含`shiro.ini`/`shiro-config.xml`；
- 依赖包中包含`shiro-core`/`shiro-web`，版本≤1.7.0（核心风险版本）；
- 请求中携带`rememberMe` Cookie，值为Base64编码的加密字符串。

## 七、漏洞与其他安全问题的叠加风险
1. **密钥泄露+反序列化**：若应用同时存在配置文件泄露（如`application.yml`中泄露Shiro密钥），会直接降低漏洞利用难度；
2. **未授权访问+反序列化**：若攻击者先通过未授权访问获取密钥配置，再利用反序列化漏洞提权；
3. **反序列化+日志注入**：若反序列化触发的代码执行权限较低，可结合日志注入进一步提权；
4. **JRMP转发+反序列化**：若目标应用出网受限，可通过JRMP利用链将反序列化请求转发至攻击者控制的服务器，绕过出网限制执行代码。

综上，Shiro反序列化漏洞的核心是“可控序列化数据+不安全的反序列化逻辑+密钥可控”，不同版本的修复仅解决了部分问题（如硬编码密钥、白名单），但只要存在“用户可控的序列化数据输入”和“无严格校验的反序列化逻辑”，就可能触发漏洞，且利用链的多样性和场景的扩展性导致该漏洞长期处于高危状态。
